BookMind Pro — how it works, and how to build it yourself

A hybrid book recommender: semantic search (sentence embeddings + FAISS) for "find books by meaning", collaborative filtering (item-item k-NN) for "readers who liked this also liked…", and an optional local LLM that tags genres offline. Everything is free and runs on a laptop.

This guide explains what each piece does, why it was chosen over the alternatives, and how it works inside, so you can rebuild the project from an empty folder instead of copying it.

Live app: yogita4-bookmind.hf.space · Source & CI/CD: github.com/YogitaPatil5/hybrid_book_recommender

How to use this guide

  1. Read sections 1–4 first. They give you the mental model: the problem, the data flow, and the maths behind each technique. Don't skip 4; every later design decision depends on it.
  2. Keep the source open next to section 6. Each function is described as what → why → how. Read the explanation, then the real code in src/bookmind/.
  3. Build along with section 10. It splits the project into ten stages. Each stage has a goal, what to write, a checkpoint test, and an exercise. Write the code yourself and look at the real file only when you're stuck.
  4. Test yourself with section 11 before a viva or interview.
The principle behind the whole project Do heavy, slow work once, offline (cleaning, LLM tagging, embedding, training), save the results as versioned files, and keep the request path small, fast and predictable. Almost every architectural choice below follows from this.

1. The problem & the idea

Two everyday questions a book app must answer:

"I want a slow-burn mystery set in winter."

The reader describes a meaning. Keyword search fails: the perfect book might never use the words "slow-burn" or "winter". We need to compare meanings. → Semantic search with sentence embeddings.

"I loved Harry Potter. What next?"

The answer often lies in behaviour, not text: people who read book A also tend to read book B, even when their descriptions differ. → Collaborative filtering over real ratings.

Each technique has a blind spot, and the other covers it:

Content-based (semantic)Collaborative filtering (k-NN)
NeedsA description per bookMany users' ratings
StrengthFree-text queries; works for brand-new books (no cold start)Captures taste and "surprising but right" links
WeaknessOnly finds books that sound similarUseless for books nobody has rated yet (cold start)
Here6,323 books (7k-books Kaggle dataset)637 books × 806 readers (Book-Crossing, 1.15M ratings)

So BookMind is hybrid. Search always uses meaning. "Similar books" tries collaborative filtering first and falls back to meaning when the ratings model doesn't know the title.

2. Big picture

There are two halves:

  • The offline pipeline (python -m bookmind.pipeline.cli …) downloads the data, cleans it, tags genres, embeds every book into a FAISS index and trains the k-NN model. Everything it produces goes into artifacts/, with checksums.
  • The web service (FastAPI) loads those artifacts once at startup. It answers HTML pages and a JSON API in milliseconds. It never trains, never calls the LLM, and never downloads anything.

4. Core concepts in depth

4.1 Embeddings — turning meaning into numbers

An embedding model maps a piece of text to a fixed-length list of numbers (a vector). It is trained so that texts with similar meaning land close together. all-MiniLM-L6-v2 outputs 384 numbers for any sentence.

"a boy discovers he is a wizard"     → [ 0.031, -0.112, 0.087, … ]   (384 numbers)
"young magician goes to magic school" → [ 0.029, -0.098, 0.091, … ]   ← very close
"a guide to tax accounting"           → [-0.140,  0.051, -0.020, … ]  ← far away

How it works inside (briefly)

  1. The text is split into sub-word tokens (WordPiece): "wizardry" → "wizard", "##ry". The vocabulary is fixed, so any word can be represented.
  2. The tokens go through 6 Transformer layers ("L6"). Self-attention lets every token look at every other token, so the vector for "bank" differs in "river bank" and "bank loan".
  3. The token vectors are mean-pooled into one sentence vector.
  4. The model was fine-tuned on about a billion sentence pairs with a contrastive objective: pull paraphrases together and push unrelated pairs apart. That is why distance means "similar meaning".

What we embed for each book

def build_text_for_embedding(row):
    title, genre, desc = s("title"), s("genre"), s("description")
    return f"{title}. {title}. Genre: {genre}. {desc}"[:MAX_EMBED_CHARS]
Why repeat the title, and why add the genre? The model mean-pools all tokens, so a long description would drown out a short title. Repeating the title gives it more weight, which helps queries that are basically a title. Adding "Genre: Mystery" places books of one genre closer together. The text is truncated because MiniLM only reads the first 256 tokens anyway.

4.2 L2 normalisation & cosine similarity

Cosine similarity measures the angle between two vectors and ignores their length:

cos(a, b) = (a · b) / (‖a‖ · ‖b‖) ∈ [−1, 1]

If every vector is first scaled to length 1 (L2 normalisation: divide by ‖a‖ = √Σaᵢ²), the denominator becomes 1 and

cos(a, b) = a · b (just a dot product)

Dot products are what CPUs and FAISS compute fastest. So we normalise once at build time (books) and once per query, then use an inner-product index. That is the whole reason for l2_normalize and IndexFlatIP ("IP" = inner product).

def l2_normalize(mat):
    arr   = np.asarray(mat, dtype=np.float32)
    norms = np.linalg.norm(arr, axis=1, keepdims=True)
    norms[norms == 0] = 1.0          # an all-zero row would divide by 0 → NaN
    return np.ascontiguousarray(arr / norms, dtype=np.float32)   # FAISS wants C-contiguous float32

Worked example: a = (3, 4) → ‖a‖ = 5 → â = (0.6, 0.8). b = (4, 3) → b̂ = (0.8, 0.6). â·b̂ = 0.48 + 0.48 = 0.96: nearly the same direction.

Why cosine and not Euclidean distance? For text vectors, the direction carries the meaning; the length mostly reflects text length and word frequency. For ratings (section 4.4), cosine compares who read a book, not how many people did. A bestseller and a niche book can still be close.

4.3 FAISS — fast nearest-neighbour search

Search means "find the k book vectors with the highest dot product with the query vector". IndexFlatIP does this exactly, as a brute-force scan written in optimised C++ with SIMD instructions. For 6,323 × 384 floats (~9.7 MB) a query takes only a few milliseconds.

index = faiss.IndexFlatIP(384)
index.add(book_vectors)                  # row i ↔ metadata row i  (ids are positions)
scores, ids = index.search(query_vec, k) # top-k by inner product = cosine

Genre filter inside the search

A naïve approach searches the top 50 and then throws away books from other genres. That can return too few results, or none. Instead we pass the allowed IDs to FAISS so it only scores books of that genre:

subset = self._genre_ids[genre]                                   # precomputed np.int64 array per genre
params = faiss.SearchParameters(sel=faiss.IDSelectorBatch(subset))
scores, ids = self.index.search(vec, k, params=params)
Exact now, approximate later Up to about a million vectors, exact search is fast enough and needs no tuning. Beyond that you would switch to IndexHNSWFlat (a graph of neighbours) or IndexIVFPQ (clusters plus compressed vectors). Only build_index changes, because the engine just calls index.search. faiss.omp_set_num_threads(1) is set because each web worker handles one small query; several OpenMP threads per query across several workers would oversubscribe the CPU.

4.4 Collaborative filtering — item-item k-NN

Build a matrix with one row per book and one column per reader. A cell is non-zero if the reader interacted with the book. Each book's row then works as a "fingerprint of who read it". Two books are similar when their fingerprints point the same way.

book \ readeru1u2u3u4
Harry Potter 11101
Harry Potter 21101
The Hobbit1001
Tax Guide0010

cos(HP1, HP2) = 3/(√3·√3) = 1.0; cos(HP1, Hobbit) = 2/(√3·√2) ≈ 0.82; cos(HP1, Tax) = 0. So the neighbours of HP1 are HP2, then The Hobbit.

  • Why item-item and not user-user? There are far fewer books than users, and books' reader sets change slowly. Item similarities are stable and can be precomputed. "Books like this one" is also exactly the feature we want.
  • Why filter active users (>200 books) and books with ≥50 readers? Book-Crossing is extremely sparse. Rows with one or two readers give noisy, meaningless cosines. Filtering keeps a dense core where similarities can be trusted. The trade-off is that only 637 books remain.
  • Why csr_matrix? Most cells are 0. A sparse matrix stores only the non-zeros, so it saves memory and speeds up the cosine computation.
  • Why algorithm="brute"? Tree indexes (KD-tree, ball tree) don't support cosine on sparse data, and with 637 rows brute force is instant.
  • Why group editions by title|author? The same book has many ISBNs (hardback, paperback…). Grouping only by title would merge different books that share a name (for example "Selected Poems", which appears 27 times).

4.5 Implicit vs explicit feedback (the bug in the original project)

In Book-Crossing a rating of 0 means "interacted but gave no score" (implicit); 1–10 is an explicit score. The original code kept those zeros and used 0 for empty cells. So "read it" and "never saw it" looked identical, and most of the signal was lost.

# simplified from pipeline/knn.py
def interaction_value(rating, mode):
    if mode == "binary":   return 1 for every row           # any interaction = 1   (default)
    if mode == "explicit": return rating where rating > 0   # implicit rows dropped
    return rating where rating > 0 else IMPLICIT_WEIGHT   # weighted: 1–10, implicit = 1

Now 0 in the matrix means only "no interaction". We didn't guess which mode is best; we measured it (next section): binary won.

4.6 Evaluation — Hit-Rate@K, coverage and leakage

  1. Split by user, 80/20. The model is trained only on the 80% of readers. If test readers' interactions were in the training matrix, the model would have already "seen the answer". That is data leakage, and it inflates scores.
  2. For each test reader with ≥2 known books: pick a seed book they read, ask for its top-K neighbours, and count a hit if any other book they read is among them. Hit-Rate@K = hits / queries.
  3. Baseline: always recommend the K most-read books. A model must be compared with something simple, or the number means nothing.
  4. Coverage: the share of the catalogue that ever gets recommended. It catches a model that "wins" by recommending the same few bestsellers to everyone.
ModelHit-Rate@5Coverage
k-NN binary (default)0.64580.7%
k-NN weighted0.57190.4%
Popularity baseline0.6880.9%
Reading this table honestly Popularity has a higher hit-rate because Book-Crossing is dominated by a handful of bestsellers that almost everyone read. But it shows the same five books to everyone (0.9% coverage) and cannot answer "similar to this book". k-NN gives up a few points of hit-rate to cover 81% of the catalogue. Reporting both metrics, and admitting the trade-off, is what makes the evaluation credible.

4.7 LLM genre tagging (offline, optional)

The raw categories field is messy (thousands of distinct strings). We map every book to one of 20 fixed genres, so genre filtering works.

  • Fixed taxonomy plus a strict prompt ("Reply with ONLY the single genre name…"), with temperature 0 for repeatable answers.
  • parse_genre doesn't trust the LLM's formatting. It tries an exact match, then "starts with a genre", then the longest genre mentioned (so "Science Fiction" wins over "Fiction"), and finally "Other". It keeps inner apostrophes so "Children's" survives.
  • Retries with exponential backoff (wait 1 s, 2 s, 4 s…) handle a busy local server. After the last retry it falls back to the keyword classifier and counts the failure. One bad book never kills a 7,000-book run.
  • Checkpoints keyed by book_id, written atomically every N rows. If you stop the job, it resumes where it left off.
  • Never at request time: an LLM call takes seconds, needs a GPU or a paid API, and can hallucinate. Tagging once offline costs nothing per request.

4.8 The hashing encoder — a test double that still works

Tests must run in seconds with no internet and no 80 MB model download. HashingEncoder uses the feature-hashing trick:

  1. Lowercase the text and split it into words; add bigrams ("magic_school") so word order matters a little.
  2. Hash each feature with blake2b → a big integer. value % 384 picks a bucket; one bit of the hash picks a sign of +1 or −1.
  3. Add the sign into that bucket, then L2-normalise.

Texts that share words share buckets, so their cosine is high. The random signs make collisions cancel out on average instead of piling up. blake2b is used instead of Python's hash() because hash() is randomised per process; we need the same vector every run. It is deterministic, has zero dependencies and keeps the same 384-dim interface. So FAISS, the API and the pipeline run for real in tests; only the model is swapped.

4.9 The hybrid strategy

find_similar(registry, title, top_k, engine="auto") prefers collaborative filtering because it is a different, behavioural signal. When the title isn't in the 637-book ratings model, it catches BookNotFoundError and uses semantic similarity over the full 6,323-book catalogue. The response says which engine answered, so the UI can change its wording ("Readers who rated this also loved…" vs "Most similar themes").

Why layers? Dependencies point one way: HTTP → services → ml/core. The services don't import FastAPI, so you can unit-test the search engine without a web server, or reuse it in a CLI or notebook. Routes stay thin: they parse input, call a service and return a schema. The src/ layout (the package lives under src/) makes tests run against the installed package, which catches packaging mistakes early.

6.1 core/ — configuration, errors, logging

core/config.py

class Settings(BaseSettings)

whatEvery setting (port, paths, limits, model name, rate limit…) as a typed field. It reads BOOKMIND_* environment variables and .env.

whyThis is the "12-factor" config pattern: the same code runs in dev, Docker and production, and only the environment changes. Types and bounds (port: int = Field(ge=1, le=65535)) turn a typo into a startup error instead of a crash hours later.

how@field_validator("rate_limit") parses "60/minute" with the limits library. @model_validator(mode="after") _cross_field_checks enforces rules between fields: default_top_k ≤ max_top_k, and no debug in production. Properties such as index_path, manifest_path and is_production keep the path logic in one place. Newer fields are validated the same way: embedding_device is Literal["cpu","cuda","mps"] (default cpu); frame_ancestors accepts only https:// origins; mounted_app_paths rejects reserved paths such as /, /api or /static.

get_settings() · @lru_cache

whatReturns one shared Settings instance. whyIt parses the environment once, and tests can call get_settings.cache_clear() or pass their own Settings to create_app.

GENRE_TAXONOMY (20 genres) · KNN_ARTIFACTS · file-name constants

whyA closed list of genres makes the LLM's job a classification task, keeps genre filters valid (a whitelist), and keeps the UI dropdown stable.

core/logging.py

whatEvery log line carries the current request's ID. Logs are JSON in production (one object per line) and readable text in dev. Files rotate with RotatingFileHandler.

whyWhen a user reports an error, they see a request_id. Search the logs for it and you get every line from that request. JSON lets log tools (ELK, Loki, CloudWatch) filter by field.

howA ContextVar is like a global variable but separate for each request, even with async concurrency. The middleware sets it, and RequestIdFilter.filter() copies it into every LogRecord. setup_logging is idempotent: it removes its own handlers before adding them, so calling it twice (tests, reload) doesn't duplicate lines. It also quietens noisy third-party loggers (httpx, huggingface_hub, transformers).

6.2 ml/embedder.py — text → vectors

class Encoder(Protocol) · name · dim · encode(texts, batch_size) → float32[n, dim]

whyA Protocol is "duck typing with type checking": anything with these attributes is an Encoder. The engine depends on the interface, not on sentence-transformers, so tests can inject HashingEncoder. This is the dependency inversion principle.

SentenceTransformerEncoder(model_name)

whatWraps MiniLM. howIt first tries SentenceTransformer(name, device=device, local_files_only=True), which loads from the local HuggingFace cache with no network. Only if the model isn't cached does it download it. It encodes in batches and passes the result through l2_normalize, so every vector has length 1. It supports both the old and the new name of the "get dimension" method, so library upgrades don't break it. The device is always explicit (default cpu): on hardware that reports a GPU, such as Hugging Face ZeroGPU, "auto" would pick CUDA, which only works inside special GPU functions.

why"Offline-first" removes the old need to set HF_HUB_OFFLINE=1 by hand. It also means startup doesn't hang or fail when Wi-Fi is down.

CachedEncoder(inner, maxsize) · encode_one(text)

whatAn LRU (least-recently-used) cache in front of any encoder, for single queries. whyPopular queries repeat; encoding is the slowest step of a search (~10–30 ms on CPU), and a cache hit takes microseconds. howAn OrderedDict plus a threading.Lock, because FastAPI runs sync endpoints in a thread pool. The cached array is set read-only so a caller can't corrupt it.

HashingEncoder(dim=384) · l2_normalize(mat) · build_encoder(settings)

See sections 4.2 and 4.8. build_encoder is a factory: it reads settings.embedding_backend and returns the right class. The index's manifest.json records which backend built it, and the engine refuses a mismatch. Mixing vector spaces would return nonsense results silently.

6.3 pipeline/ — the offline jobs

io.read_csv(path, required) · io.write_csv_atomic(df, path)

whatSafe CSV input and output. read_csv turns missing files, bad encodings and missing columns into clear DataValidationErrors. howwrite_csv_atomic writes to a temp file in the same folder and then os.replaces it. A rename on the same disk is atomic, so an interrupted run (Ctrl+C, power loss) never leaves a half-written file that the next step would trust.

download.download_datasets(data_dir, which, downloader, force)

whatIt calls kagglehub.dataset_download("dylanjcastillo/7k-books-with-metadata") and "ra4u12/bookrecommendation", finds the CSVs in the cache (_find searches recursively, because layouts differ) and copies them to data/books_raw.csv and data/bx/. whyReproducible: anyone can rebuild from the same public sources. The downloader parameter is injected so tests can use a fake instead of the network. Files that already exist are skipped unless you pass --force.

prepare.prepare_dataframe(df, min_description_chars=30) → (df, PrepareReport)

howStep by step:

  1. Check the required columns, or raise DataValidationError.
  2. clean_text each field: unescape HTML entities, strip tags, replace non-printable characters, collapse whitespace.
  3. normalise_authors: "A;B" → "A, B". normalise_isbn13 keeps 13 digits only.
  4. Thumbnails: http:// → https://, and anything that isn't https (for example javascript:) is dropped. This matters because the page's CSP only allows https images.
  5. _numeric(series, lo, hi) coerces to numbers and blanks out-of-range values (a rating of 7 on a 0–5 scale, the year 3020).
  6. Drop rows without a title or description, or with a description that's too short to embed meaningfully.
  7. De-duplicate by ISBN, then by title|author.
  8. _make_book_id: use the ISBN-13 if there is one, else "h" + sha1(title|author)[:15]. A stable ID survives re-runs, which is why classification checkpoints can resume.

It returns a PrepareReport (input, kept, dropped for each reason), so you can see what cleaning did. Our run kept 6,810 → 6,323 rows.

classify.parse_genre · KeywordClassifier · OllamaClassifier · run_classify

See section 4.7. KeywordClassifier scores each genre by regex matches on \b word starts. The \b matters: without it "teen" matched inside "Nineteen" and tagged history books as Young Adult (a real bug that was found and fixed). OllamaClassifier.check_available() fails fast if the server is down or the model isn't pulled. That beats finding 7,000 fallbacks at the end. Its client and sleep are injectable, so tests don't actually wait.

build_index.build_index(input_csv, artifacts_dir, encoder, batch_size)

howBuild each book's text (section 4.1) → encoder.encode in batches → faiss.IndexFlatIP(dim).add(vectors) → prepare_metadata (the columns the app needs, row-aligned with the index) → save_artifacts. whyRow i of the parquet file is vector i in FAISS, so there's no separate ID mapping to keep in sync.

knn.load_books / load_ratings / build_interactions / build_pivot / fit_model / save_knn_artifacts / train_knn

howRead the BX files (;-separated, latin-1, with some broken lines skipped) → normalise ISBNs (upper case, digits and X only) → validate ratings 0–10 → join → interaction_value → group editions → filter active users and popular books → keep one row per (user, book), using the strongest signal → make display titles unique ("Title (Author)" when two books share one) → pivot → csr_matrix → NearestNeighbors(brute, cosine).

save_knn_artifacts writes four pickles (model, pivot, title list, ratings table) plus knn_manifest.json, which records the SHA-256 of each file, the scikit-learn version, the mode, the counts and the training time. KnnConfig.validate() rejects impossible thresholds before any work is done. It also records library_versions (numpy, pandas, scipy, scikit-learn) so a deployment can install exactly the versions that wrote the pickles.

knn.evaluate_knn(interactions, k=5, test_fraction=0.2, seeds_per_user=5, random_state=42) · run_evaluation

See section 4.6. A fixed random_state makes the result reproducible: the same numbers every run. --compare-modes rebuilds the interactions for each mode and evaluates them all, so the choice of default is backed by data.

cli.main(argv) · build_parser()

whatAn argparse CLI with sub-commands (download, prepare, classify, build-index, train-knn, evaluate-knn, all). howEach sub-command calls one library function. all chains them and trains k-NN only if the BX files exist. Errors are caught at the top: a BookMindError prints a clean message and returns exit code 1, which is the convention scripts and CI rely on. main(argv) takes a list, so tests call it directly without spawning a process.

6.4 services/ — the business logic

services/validation.py

clean_text(value, field, max_length) · validate_top_k(value, max_top_k) · validate_genre(value, allowed)

howclean_text: reject None and non-strings → NFKC unicode normalisation (so a full-width "Ａ" becomes "A" and look-alike tricks fold away) → drop non-printable control characters → collapse whitespace → must be non-empty and ≤ 300 chars. validate_top_k rejects booleans (in Python True is an int!) and anything outside 1…max. validate_genre matches case-insensitively against the whitelist and returns the canonical spelling, or "All".

whyPydantic validates the types at the HTTP edge, but the services validate again, because they're also called from the CLI, the web pages and tests. Defence in depth: a limit on input size also caps the CPU cost of each request.

services/artifacts.py

Manifest · sha256_file · save_artifacts · load_manifest · load_artifacts

whatA versioned, verifiable bundle: book_index.faiss, book_meta.parquet, and manifest.json {schema_version, created_at, embedding backend and model, dim, num_books, the SHA-256 of both files}.

howsave_artifacts writes the data files atomically and the manifest last. If the build dies halfway there is no manifest, and the app treats the index as "not built" instead of loading half of it. sha256_file reads in 1 MB chunks, so memory stays flat for big files. load_artifacts cross-checks everything: files exist, schema version is supported, checksums match, index.ntotal == len(meta) == manifest.num_books, dimensions match, and the required columns exist.

whyA corrupt or mismatched index would quietly return the wrong books, which is much worse than an error. Checksums catch disk corruption, a partial copy, or someone editing a file by hand.

services/semantic_search.py — SemanticSearchEngine

from_artifacts(settings, encoder) · __init__(index, meta, encoder, manifest, …)

howLoad and verify the artifacts → check the encoder matches the manifest (backend and dimension) → wrap it in CachedEncoder → precompute everything a request needs: _records (cleaned rows as small dataclasses), _title_positions (lower-case title → rows), _genre_ids (genre → int64 array for IDSelectorBatch), and _titles_lower. whyAll heavy work happens once at startup, so each request does almost nothing besides one FAISS call. The engine is read-only after construction, and that makes it thread-safe without locks.

_make_record(row) · _to_book(pos, score) · truncate(text, limit)

Turn a pandas row into clean Python values (NaN → None, http → https cover) and then into the Book schema, including buy_links. truncate cuts descriptions on a word boundary and adds "…" only when it actually shortened something.

search(query, genre=None, top_k=12)

howValidate → encoder.encode_one(query) → _knn(vec, top_k × overfetch, genre) → pin an exact title match to the top (if you type a title exactly, you expect that book first) → _collect → log the timing. why overfetch? One book can have several editions in the data. We ask FAISS for extra results so there are still top_k left after _collect removes duplicates.

_knn(vec, k, genre) · _collect(hits, top_k, exclude_titles, pinned, scores_visible)

_knn runs the FAISS search, with IDSelectorBatch when a genre is set (section 4.3), and drops -1 ids (FAISS's "no result" marker). _collect walks the hits in order and skips excluded titles and repeated title|author keys, so one card per book. It stops at top_k. scores_visible=False is used by browse, where a "similarity" number would be meaningless.

resolve_title(title) · similar(title, top_k)

resolve_title maps what the user typed to one row: an exact match, then a prefix match, then a substring match. Among candidates it prefers the shortest title, then the edition with the most ratings (_best_edition). If nothing matches it raises BookNotFoundError with autocomplete suggestions in details, which the UI shows as "Did you mean…". similar doesn't re-encode the title. It uses index.reconstruct(pos) to fetch the book's stored vector, which carries its whole description, and excludes every edition of the source book.

browse(genre, top_k) · popular(n) · autocomplete(prefix, limit) · list_genres()

browse powers genre-only search: the books in that genre sorted by (ratings_count, avg_rating), with no query. popular is the same across all books. autocomplete returns unique titles, prefix matches before substring matches.

services/knn_recommender.py — KnnRecommender

verify_knn_manifest(dir) · from_artifacts(dir, …) · recommend(title, top_k) · popular(n) · autocomplete

howverify_knn_manifest checks the checksums before unpickling. Unpickling runs code, so you only unpickle files you can prove are the ones you wrote. It also warns if the scikit-learn version differs from the training version. recommend: clean the title → look it up case-insensitively → model.kneighbors(row, n_neighbors=top_k+1) (the +1 is because the nearest neighbour of a book is itself) → skip itself → score = 1 − cosine distance. popular computes the average rating from explicit ratings only and divides by 2 to show /5. That way implicit zeros don't drag the average down, and the scale matches the rest of the UI.

services/registry.py — ServiceRegistry

ServiceRegistry.load(settings, encoder) · _load_semantic · _load_knn · require_semantic() · knn_status · errors

whatIt holds the engines for the whole app. It tries to load each one and records failures instead of crashing. knn_status is one of loaded, absent, disabled or failed.

whyThis is graceful degradation. If the k-NN files are missing, the app still searches. If the index is missing, the pages still load and show a banner telling you how to build it, the API returns a clean 503, and /health/ready reports why. A crash loop would tell the user nothing. require_semantic() is the single place that converts "not loaded" into a ServiceUnavailableError.

services/recommendation.py — the hybrid layer

find_similar(registry, title, top_k, engine) → (matched_title, engine_used, books)

See section 4.9.

autocomplete(registry, query, limit) · popular_titles(registry, limit, genre) · popular_books · catalogue_stats

autocomplete merges suggestions from both catalogues: prefix matches first, de-duplicated case-insensitively. popular_titles powers the "Popular books" dropdown. With a genre it uses browse. Otherwise it interleaves the k-NN and semantic popular lists (k-NN first, because those titles also get "readers who liked this" results). catalogue_stats builds the /api/v1/stats response: book counts, model names, k-NN mode and training time.

services/buy_links.py

build_query · amazon_link · flipkart_link · google_books_link · get_buy_links

These build retailer search URLs with urllib.parse.quote_plus. whyGuessing product IDs would produce broken or wrong links. A search URL always works and is honest.

6.5 HTTP layer — middleware, API, pages, errors

middleware/request_context.py — RequestContextMiddleware.dispatch

howTake the incoming X-Request-ID if it matches a safe pattern (so it can't be used to inject into the logs), or generate uuid4().hex → set the ContextVar → time the request → in finally (so it runs even on errors): increment the Prometheus counter and histogram labelled by the route template (/api/v1/search, not /api/v1/search?q=harry), write one access-log line, reset the ContextVar → add X-Request-ID and the security headers to the response.

why the route template? Metric labels must have bounded cardinality. Labelling by raw URL would create a new time series for every query and eventually exhaust Prometheus's memory. The template comes from request.scope["route"].path.

security headers A strict Content-Security-Policy (scripts only from our own origin, so no inline scripts and an XSS can't run injected code), X-Content-Type-Options: nosniff, X-Frame-Options: DENY (prevents clickjacking), Referrer-Policy and Permissions-Policy. HSTS is set only in production, because it forces https and would break plain-http localhost. The /docs page gets a relaxed CSP because Swagger UI needs its CDN. Two settings adjust this for hosting: frame_ancestors replaces frame-ancestors 'none' with the allowed origins and drops X-Frame-Options (used on the Space, where huggingface.co frames the site), and mounted_app_paths leaves a mounted sub-app such as Gradio at /demo without our CSP. Both are off by default.

middleware/rate_limit.py — RateLimitMiddleware (pure ASGI)

howKey = client IP → MovingWindowRateLimiter.hit("60/minute"). If the request is allowed, pass it on. If not, return 429 in the standard error envelope with a Retry-After header. /health, /metrics and /static are exempt, so a monitoring system or a page's CSS is never throttled. If the storage (e.g. Redis) is down, it fails open (allows the request) and logs the error. A broken limiter shouldn't take the whole site down. Paths in mounted_app_paths are exempt too.

why a moving window? A fixed window lets a client send 60 requests at 12:00:59 and 60 more at 12:01:00, which is 120 in one second. A moving window counts the last 60 seconds at any moment. why pure ASGI? It's cheaper than BaseHTTPMiddleware and runs before any routing happens.

api/deps.py — get_registry · get_app_settings · get_semantic_engine

FastAPI dependency injection: routes declare engine = Depends(get_semantic_engine). The objects live on app.state, so tests can build an app around a small registry and every route uses it automatically. No globals.

api/v1/routes.py — search_books · similar_books · autocomplete · list_genres · stats

GET /api/v1/search: q is optional. With q, run engine.search. With only genre, run engine.browse. With neither, return 422 "Provide a search query (q), a genre, or both". /books/similar calls find_similar with engine=auto|semantic|knn. /autocomplete with an empty q returns {"mode":"popular","label":"Popular books"}. Each route declares response_model=…, so the output is validated and documented in /docs. A legacy /api/search stays for old clients and is marked deprecated.

why sync def, not async def? Encoding and FAISS are CPU-bound and blocking. FastAPI runs sync endpoints in a thread pool, so the event loop keeps serving other requests. An async def doing CPU work would block everyone.

api/health.py — live · ready · metrics

/health/live never touches dependencies; it answers "is the process alive?" (Kubernetes restarts the container if this fails). /health/ready reports each component: ready (200), degraded (200, k-NN failed but search works), or unavailable (503, so the load balancer stops sending traffic). Two separate probes exist because a container that's alive but still loading should not be restarted, only kept out of traffic.

api/errors.py — wants_json · error_response · handlers · register_exception_handlers

Four handlers: BookMindError → its status and code; FastAPI's RequestValidationError → 422 with field details; HTTPException (404 for unknown routes, 405…) → same envelope; any other Exception → 500 "internal_error". The stack trace is logged but never sent to the client, because leaked internals help attackers. wants_json returns JSON for /api/* or Accept: application/json, and a friendly error.html page for browsers.

{"error": {"code": "validation_error", "message": "top_k must be between 1 and 50.",
           "request_id": "3f9c…", "details": {"field": "top_k"}}}
web/routes.py — home · search_page · recommend_get / recommend_post · about · _render

Server-rendered pages that call the same services as the API, so behaviour can't drift between them. search_page supports genre-only browsing. Recommend accepts GET ?q= (shareable links) and POST (the form). A BookNotFoundError is shown inline with suggestions instead of an error page. _render adds the shared context (version, whether search is ready, whether k-NN is available) to every page.

6.6 main.py & __main__.py

create_app(settings=None, registry=None) → FastAPI

whatThe app factory. howSet up logging → define a lifespan context manager that runs ServiceRegistry.load at startup (unless a registry was injected) → create the FastAPI app (with docs disabled in production) → templates → middleware → mount /static → include the routers → register the error handlers.

why a factory? Each test can create a fresh app with its own settings and fake registry; with a global app = FastAPI() state would leak between tests. A module-level __getattr__("app") still allows uvicorn bookmind.main:app, and importing the module has no side effects.

middleware order Starlette wraps middleware so that the last one added runs first. We add RateLimit, GZip, CORS, TrustedHost, then RequestContext, so RequestContext is the outermost layer. Even a 429 or a rejected host therefore gets a request ID, a log line and security headers.

__main__.py — port_is_free · find_free_port · build_parser · main

python -m bookmind [--port] [--host] [--open] [--reload]. port_is_free tries to bind a socket. In development, if the port is busy, find_free_port tries the next ones and logs "Port 8000 is busy — using port 8001 instead". In production it keeps the configured port, so a misconfiguration fails loudly instead of the service silently moving. --open starts a timer thread that opens the browser after the server is up. uvicorn runs with log_config=None so our logging setup isn't overwritten.

6.7 Front-end — templates, themes, autocomplete

templates/base.html · _macros.html (imported "with context") · pages

Jinja2 inheritance: base.html holds the nav, footer and theme toggle; pages fill {% block content %}. Macros render book cards. They're imported with context so url_for can see request (without it you get KeyError: 'request', a bug hit during development). Jinja auto-escapes all output, so a book title containing <script> renders as text.

static/js/theme.js (in <head>) · main.js · css/style.css

how themes workAll colours are CSS custom properties (--bg, --text, --accent…). They're defined for light in :root and redefined in :root[data-theme="dark"]. theme.js is a tiny synchronous script in <head>. It picks the saved choice from localStorage, else the OS preference (prefers-color-scheme), and sets data-theme before the first paint, so the page never flashes the wrong theme. main.js handles the toggle button, saves the choice, follows OS changes until the user picks one, and runs the mobile menu, "show more" and the broken-cover fallback. All scripts are external files, which is what the strict CSP requires.

static/js/autocomplete.js

On focus or click with an empty box, it fetches /api/v1/autocomplete?q=&genre=… and shows "Popular books" (or "Popular in Fantasy"). From the first typed letter it fetches suggestions, debounced (it waits a few ms after the last keystroke) so it doesn't send one request per key. An AbortController cancels the previous request when a new one starts, so an old, slow response can never overwrite newer suggestions. Keyboard support: ↑/↓/Enter/Esc, with ARIA attributes (role="listbox", aria-activedescendant) for screen readers. Suggestions are inserted with textContent, never innerHTML, which prevents XSS.

8. Testing strategy

Unit tests (17 files)

Each function in isolation: validation edge cases, parse_genre outputs, the hashing encoder's determinism, manifest checksum failures, k-NN encodings, the port fallback, logging formatters, the Hugging Face packaging script.

Integration tests (5 files)

A real FastAPI app via TestClient: every endpoint, the error envelope, rate limiting (429 + Retry-After), security headers (including frame-ancestors and mounted paths), themes, hybrid fallback, degraded mode.

Deployment tests

test_prepare_hf_space.py checks the Space package (files, zip contents, pinned versions, the README metadata limits), the retry rules, the upload against a fake Hugging Face client, and that the workflows are valid YAML with the release gate in place.

End-to-end

Runs the CLI pipeline on fixture CSVs → builds real FAISS and k-NN artifacts → starts the app on them → searches. It proves that all the pieces fit together.

Fakes, not mocks of everything

HashingEncoder replaces MiniLM; tests/bx_fixture.py generates small Book-Crossing files with known clusters (cluster_of), so tests can assert that "a fantasy book's neighbours are fantasy books". FAISS and scikit-learn run for real.

Key fixtures in tests/conftest.py: make_settings(**overrides) (validated settings pointing at a temp dir), built_dir (a ready artifacts folder), write_knn_artifacts, and clients for the API. Each test gets a fresh app through create_app(settings, registry).

python -m pytest                          # 529 tests, ~99% coverage (CI fails below 85%)
python -m pytest tests/unit -q            # just the fast unit tests
python -m pytest -k autocomplete          # tests whose name matches
python -m pytest --cov --cov-report=html  # browse htmlcov/index.html
How to write a good test here Arrange a tiny dataset where you know the right answer, act through the public function, and assert behaviour, not implementation. For every bug you fix, first write a test that fails (for example "Nineteen must not be tagged Young Adult"), then fix the code. This is called a regression test.

9. Deployment & CI/CD

The app is live at https://yogita4-bookmind.hf.space. Every push to GitHub is tested automatically, and only a fully green run is deployed. This section explains each piece and why it is there.

9.1 Running it: laptop, server, Docker

  • Laptop: run.bat / run.sh use the venv's Python directly (no activation), build the index if it's missing, then start python -m bookmind --open.
  • Dockerfile (multi-stage): a builder stage installs the dependencies (CPU-only torch); the runtime stage copies only the virtualenv and the code, runs as a non-root user, sets a HEALTHCHECK on /health/live, and can preload the model at build time (PRELOAD_MODEL) so containers start offline.
  • gunicorn.conf.py: the uvicorn_worker.UvicornWorker class, the worker count from BOOKMIND_WORKERS, timeouts and graceful shutdown, and max_requests with jitter (workers recycle periodically, which caps slow memory leaks).
  • docker-compose.yml: web + redis (shared rate-limit store across workers) + a pipeline service under a profile.

9.3 The live Space: why a Gradio Space serves a FastAPI site

Free Hugging Face accounts can no longer run Docker Spaces, and new free accounts only get Gradio + ZeroGPU. A Gradio Space simply runs python app.py and shows whatever answers on port 7860. So deploy/gradio/app.py starts the same FastAPI website you run locally, and mounts a small Gradio screen at /demo.

deploy/gradio/app.py — extract_package(archive, target)

whatUnpacks bookmind.zip (code, templates, CSS/JS) into a temporary folder and adds it to sys.path. whyJinja2 templates and static files must be real files on disk. howBefore extracting, every member path is resolved and must stay inside the target folder. This is zip-slip protection: a name like ../../x is rejected.

SPACE_DEFAULTS → create_app(settings, registry=registry) → gr.mount_gradio_app(…, path="/demo", ssr_mode=False)

The settings are set with os.environ.setdefault, so the Space's own variables can still override them: ENV=production (HTTPS-only headers), ENABLE_DOCS=true, LOG_TO_FILE=false, FRAME_ANCESTORS=["https://huggingface.co"] (the Space page shows the site in a frame; otherwise the CSP forbids framing), and MOUNTED_APP_PATHS=["/demo"] (Gradio ships inline scripts, so the strict CSP and the rate limiter skip that path). The engines are loaded once and shared by both front ends. ssr_mode=False is needed because Hugging Face enables Gradio's server-side rendering, which starts a Node.js server on port 7860 and causes Errno 98: address already in use.

@spaces.GPU _zerogpu_placeholder() · report_zerogpu_startup()

whatZeroGPU requires at least one GPU function to be reported when the app starts. The spaces library normally sends that report from inside Gradio's launch(). This app starts uvicorn itself, so it calls spaces.zero.startup() directly. Without that call the Space stops with "No @spaces.GPU function detected during startup". The placeholder function is never called, because BookMind runs on CPU (BOOKMIND_EMBEDDING_DEVICE=cpu). ZeroGPU reports a GPU that only works inside GPU functions, so loading the model onto it would break searches.

uvicorn.run(app, port=7860, proxy_headers=True, forwarded_allow_ips="*")

Hugging Face's proxy terminates HTTPS and forwards the request. Trusting its X-Forwarded-Proto and X-Forwarded-For headers makes generated links https:// (so browsers don't block them as mixed content) and lets the rate limiter count each visitor separately rather than treating everyone as the proxy.

build_demo() · search() · recommend() · render() · _card()

The Gradio screens at /demo. They are thin wrappers over the same services: engine.search, engine.browse, find_similar, catalogue_stats. All book text is HTML-escaped (_e), and broken covers fall back to a CSS background image, because Gradio strips inline onerror handlers.

9.4 Building the Space package — scripts/prepare_hf_space.py

check_artifacts(artifacts) · _check_out(root, out)

The index, metadata and manifest must exist, and the index must be built with sentence-transformers (the hashing test encoder would give poor results). Missing k-NN files only produce a warning. _check_out refuses output folders that would delete the project, such as the project root, src or artifacts.

trained_versions(artifacts) · gradio_requirements(lookup, python, trained, on_ci)

whyThe k-NN files are pickles of pandas and scikit-learn objects, and they may not load under different library versions. howtrain-knn records numpy, pandas, scipy and scikit-learn versions in knn_manifest.json, and the Space's requirements.txt pins exactly those. Other libraries are pinned to the installed version when it supports the Space's Python (3.12, checked with packaging), and otherwise get a safe range. On GitHub Actions it warns if versions weren't recorded.

check_space_card(text)

Validates the Space README's metadata before uploading: it must start with a --- block, be valid YAML, have no unfilled {placeholder}, and have a short_description of at most 60 characters. A real deploy failed on exactly that last rule, and this check now catches it locally.

_zip_package · _prepare_gradio · _prepare_docker · prepare(root, out, sdk)

Builds a flat folder of 12 files (app.py, README, requirements, bookmind.zip, 8 artifacts), so it can also be dragged into a browser uploader. --sdk docker builds the folder for a paid Docker Space instead.

upload(out, repo_id, api, sdk) · _retry · _is_network_error · _is_auth_error · _is_client_error

Uses huggingface_hub to check the login, create the Space if needed and upload the folder. _retry retries only network errors (connection resets, timeouts, HTTP 408/429/5xx). A 401/403 response becomes a clear "token or email" message, and any other error is reported as it is, rather than being mislabelled as a network problem. The api object is injectable, so the tests use a fake client with no network.

Lessons from the real deploymentEach problem was found by a failing check or a live error and fixed: Docker being paid on free accounts, a network cutting uploads, CI failing on GitHub because of GITHUB_ACTIONS=true, a 67-character description, the ZeroGPU startup report, and Gradio SSR taking the port. The full table is in docs/REVIEW_AND_CHANGES.md.

11. Self-check quiz

Why do we L2-normalise vectors before using IndexFlatIP?For unit vectors the inner product equals the cosine similarity, and an inner product is the fastest thing to compute. Without normalising, long vectors would score higher for no reason.
Why is the LLM not called when a user searches?Latency (seconds), cost or a GPU, and non-determinism or hallucination. Genres change rarely, so tagging them once offline gives the same benefit for free.
What is data leakage and how does evaluate_knn avoid it?Leakage is when test information is used during training, which inflates the scores. We split users 80/20 and fit the pivot on training users only.
Popularity has a higher hit-rate than k-NN. Why don't we use it?It recommends the same five books to everyone (0.9% coverage) and can't answer "similar to this book". Hit-rate alone rewards that behaviour, so we also report coverage.
What does Book-Crossing's rating 0 mean, and why did it matter?"Interacted without a score" (implicit). The original treated it the same as "never read", which deleted most of the signal. We encode any interaction as 1.
Liveness vs readiness?Liveness: is the process alive (if not, restart it)? Readiness: can it serve traffic (if not, stop routing to it, but don't restart)?
Why is the manifest written last?If the build crashes, there's no manifest, so the app sees "not built" instead of loading a half-written index.
Why verify checksums before unpickling the k-NN files?Unpickling can execute code. Only load files you can prove are the ones the pipeline wrote.
Why are metric labels the route template rather than the URL?To keep cardinality bounded. Every distinct URL would become a new time series and grow memory without limit.
Why are the API endpoints plain def and not async def?Their work is CPU-bound and blocking (encoding, FAISS). FastAPI runs sync endpoints in a thread pool, keeping the event loop free.
How does the theme avoid a flash on load?A synchronous script in <head> sets data-theme before the first paint; all colours are CSS variables switched by that attribute.
What happens if the k-NN files are missing?knn_status = "absent"; "similar books" uses the semantic engine; /health/ready still says ready, because k-NN is optional.
What does the Deploy workflow wait for, and why?For the CI workflow to finish with success on main. It's a release gate: a failing test, lint or type check can never reach the live site.
Why does the Space pin pandas and scikit-learn to specific versions?The k-NN files are pickles of pandas and scikit-learn objects and may not load under other versions. train-knn records the versions, and the Space installs exactly those.
Why does app.py call spaces.zero.startup() itself?ZeroGPU requires a GPU function to be reported at startup. The spaces library does that inside Gradio's launch(), which this app doesn't use, because it serves the FastAPI site with uvicorn.
Why ssr_mode=False when mounting Gradio?Hugging Face turns on Gradio's server-side rendering, which starts a Node.js server on port 7860, the port the website must use. The website renders its own HTML, so SSR isn't needed.
Why trust X-Forwarded-* headers on the Space?The proxy terminates HTTPS. Without trusting it, links would be http:// (and blocked as mixed content), and every visitor would share one rate-limit bucket under the proxy's IP address.

12. Glossary

TermMeaning
EmbeddingA fixed-length vector that represents meaning; similar meaning gives nearby vectors
Cosine similarityThe cosine of the angle between two vectors; 1 = same direction, 0 = unrelated
FAISSFacebook AI Similarity Search, a library for fast nearest-neighbour search over vectors
k-NNk-nearest neighbours: the k closest items under a distance metric
Collaborative filteringRecommending from the behaviour of many users rather than from item content
Implicit feedbackInteractions without an explicit score (read, clicked, bought)
Cold startA new item or user with no interaction history
Hit-Rate@KThe share of queries where a relevant item appears in the top K
CoverageThe share of the catalogue that the system ever recommends
Data leakageTest information influencing training, which gives over-optimistic scores
Feature hashingMapping features to a fixed number of buckets with a hash function
ASGIThe async Python web server interface (what uvicorn speaks)
MiddlewareCode wrapped around every request (logging, security, limits)
Dependency injectionPassing collaborators in (here via Depends) instead of creating them inside, so they're easy to swap in tests
CSPContent-Security-Policy, a browser rule for which sources may run scripts, load images, and so on
Atomic writeWrite to a temp file, then rename, so readers see the old file or the new one but never half of it
Graceful degradationKeep serving what still works when a component fails
ArtifactA file produced by the pipeline and consumed by the service (index, model, manifest)
CI / CDContinuous integration (automatically test every change) / continuous deployment (automatically release changes that pass)
GitHub ActionsGitHub's automation service; runs the workflows in .github/workflows/ on GitHub's servers
Release gateA rule that blocks a release unless checks pass (here: Deploy only after green CI)
SecretAn encrypted value (like an API token) stored in GitHub and given to workflows, never written in the code
Hugging Face SpaceFree hosting for ML demos; a Gradio Space runs python app.py and serves port 7860
ZeroGPUHugging Face hardware that lends a GPU only to functions marked @spaces.GPU
SSRServer-side rendering, where HTML is produced on the server (Gradio uses a Node.js server for it)
Reverse proxyA server in front of the app that handles HTTPS and forwards requests, adding X-Forwarded-* headers
PicklePython's object serialisation format; tied to library versions and unsafe to load from untrusted sources
