## B. 5-minute demo script

1. **Problem (30 s)** — "Keyword search can't find books by meaning, and pure popularity shows
   everyone the same bestsellers. BookMind combines content-based and collaborative recommendations."
2. **Search by vibe (60 s)** — `/search`: click the empty box → *Popular books* dropdown. Type
   "a story about forgiveness" → results match meaning, not words. Clear the box, pick only a genre →
   most popular books in that genre. Toggle light/dark mode (top-right).
3. **Hybrid recommendations (60 s)** — `/recommend` → a Book-Crossing title (e.g. a Harry Potter book):
   "Readers who rated this book also loved these" (k-NN). Then a title only in the 7k catalogue:
   wording changes to "most similar themes" (semantic fallback).
4. **API & engineering (60 s)** — `/docs` (try `/api/v1/search`), `/health/ready`, `/metrics`.
   Send `top_k=1000` to show validation and the error format with `request_id`.
5. **Quality (60 s)** — run `python -m pytest --cov` live; show the evaluation table and explain why
   coverage matters next to hit-rate.
6. **Wrap-up (30 s)** — Docker, CI, no paid APIs, everything reproducible from two Kaggle datasets;
   live on Hugging Face Spaces (Gradio front end), so anyone can try it without installing anything.

## C. Likely viva questions

**Q: Does it use an LLM or k-NN?**
Both, in different roles. Search uses sentence embeddings + FAISS (itself a nearest-neighbour search
over meaning). Collaborative filtering is an item-item k-NN over reader ratings. The LLM runs only
offline to tag genres — never at request time (latency, cost, hallucination).

**Q: Why cosine distance?**
It compares the *pattern* of who read a book, not the magnitude, so a bestseller with 300 readers and
a niche book with 50 can still be close if the same people read them.

**Q: Why is popularity's hit-rate higher than k-NN's?**
Book-Crossing is dominated by a few bestsellers, so recommending them "hits" often — but it recommends
the same 5 books to everyone (0.9% coverage) and can't answer "similar to this book". That's why we
report coverage alongside hit-rate; k-NN gets 64.5% hit-rate with 80.7% coverage (popularity: 68.8% hit-rate, 0.9% coverage).

**Q: What was wrong with the original k-NN?**
Book-Crossing uses 0 for "interacted without rating"; the original kept those zeros and also used 0 for
"never read", so the two were indistinguishable. We encode any interaction as 1 (binary), chosen after
comparing three encodings with `evaluate-knn --compare-modes`. Editions are grouped by title + author.

**Q: How do you avoid data leakage in evaluation?**
Readers are split 80/20 *before* training; the model never sees test readers' interactions.

**Q: What makes it production-grade?**
Validation at every boundary, typed errors with stable codes, structured logs with request IDs,
health/readiness probes, Prometheus metrics, rate limiting, security headers, checksummed artifacts,
degraded mode instead of crashing, 528 tests at ~99% coverage, strict typing, Docker and CI.

**Q: How would it scale?**
FAISS supports approximate indexes (IVF/HNSW) for millions of vectors; workers are stateless so they
scale horizontally behind a load balancer; Redis shares rate limits; the k-NN can move to an
approximate index or matrix factorisation for larger rating sets.

**Q: Cold start?**
A new book with no ratings is still searchable and recommendable through its description (semantic
engine); collaborative filtering takes over once it has readers.

**Q: Can it use bigger or live data?**
Yes — see `docs/ROADMAP.md`. Only the `prepare` step knows dataset columns; FAISS switches to an
approximate index (HNSW/IVF) for millions of books; live data comes from free APIs (Open Library,
Google Books) as a cached fallback, with new books embedded by a scheduled job.

**Q: Why is the LLM not used at request time?**
Genre tagging happens once offline. At request time an LLM would add seconds of latency, need a GPU or a
paid API, and could hallucinate; embeddings + FAISS answer in milliseconds and deterministically.

**Q: How does the dark/light theme avoid a flash on load?**
A tiny script in `<head>` (`theme.js`) sets `data-theme` from `localStorage` or the OS preference before the
page paints; every colour is a CSS custom property redefined for each theme.

**Q: How is it deployed?**
Locally as a FastAPI service (gunicorn + uvicorn workers, Docker image, health checks). The public demo
runs free on Hugging Face Spaces as a **Gradio front end over the same service layer**: `app.py` calls the
same `SemanticSearchEngine`, `KnnRecommender` and hybrid `find_similar` as the website and API. That is
the payoff of keeping business logic out of the web layer — a new interface was a single file. The
k-NN pickles need the same pandas/scikit-learn versions they were trained with, so the deploy script
pins the Space's requirements to the versions on the build machine.

**Q: Limitations / future work?**
Titles differ between the two datasets, so collaborative filtering covers only Book-Crossing titles;
next steps would be ISBN linking across catalogues, a cross-encoder re-ranker, hybrid BM25 + vector
search, and an A/B test of recommendation clicks.
